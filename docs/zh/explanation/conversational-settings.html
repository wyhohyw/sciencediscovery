PRODUCT REVIEW · SCENARIOS & DIAGRAMS

完整设计 v12 · 评审版

v12 / 评审讲解版 · 2026.10.19 · 13 章 · 连续全文

从用户问题和一条 PubMed 任务讲起，配六张流程与卡片示意。无需先了解 issue；当前实现与目标设计分别说明。

文档说明

这项功能要解决的事情很具体：用户正在做研究，却因为缺少一个模型或工具，被迫离开对话去找设置。我们希望 Agent 把需要改的内容带到对话里，用户确认后，原任务接着做。

本文面向第一次了解该功能的产品、研发和科研业务评审。它包含完整设计，也提供具体例子、界面示意和讲解顺序；不需要先读 issue 或历史修订。

  • 想先理解体验：读第 1～4 节；想讨论长任务和实现方式：再读第 8～10 节。
  • 需要核对交付：读第 2、12、13 节。图中的“目标设计”不代表当前全部完成。
  • 技术契约见完整开发文档 v4，实测记录见实现与实测 v4。开发 v4 的技术约束仍适用，本版主要改进产品解释方式。
  • 文档日期：2026-10-19。当前为隔离分支中的有限实现，不表示已合入主仓；具体交付与验证范围在正文中分别说明。

1. 为什么做：研究任务不应该变成找设置的任务

1.1 一个用户会遇到的场景

用户对 ScienceDiscovery 说：“用 PubMed 找几篇 TP53 相关论文，给我标题和来源。”

TP53 在这里是一个检索关键词；理解和评审这项配置功能不需要先了解相关研究背景。

PubMed 是文献数据源。ScienceDiscovery 通过“连接器”调用它：可以把连接器理解为系统接入某个外部工具的入口。即使系统已经安装 PubMed 连接器，它也可能尚未在用户当前的对话中启用。

此时，用户真正想做的是查论文，却要先理解“连接器在哪个设置页”“改完影响谁”“是否还要重新提问”。不常用的配置尤其难找；长任务执行到一半遇到这个问题，还可能丢失任务的连续感。

1.2 预期改变

用户不需要先知道设置项叫什么、位于哪里。Agent 说明“这一步缺什么、为什么需要、只会改哪里”，系统提供相应的选择或输入，用户完成一次明确确认。

设置页继续用于集中管理；对话卡解决的是“做任务时，顺手完成必要配置”。已有设置能完成任务时，直接执行，不为了展示功能弹卡。

1.3 先认识几个必要的词

本文用词 对评审而言是什么意思
Agent（研究助手） 接受研究目标、调用模型与工具、组织执行步骤的软件助手
主 Agent / 子 Agent 主助手可以自己做，也可把部分工作委派给另一个助手；两者可能有不同预设工具
会话（Session） 用户当前打开的这段研究对话
一次任务（run） 用户提交一次研究要求后，系统执行这项要求的记录
连接器 ScienceDiscovery 调用 PubMed 等外部工具的入口
配置服务/适配器 后端的公共配置流程，以及每类设置各自的校验和写入逻辑

本文先讲用户操作；run ID、检查点等只在解释“怎样保证任务接着做”时使用。

2. 先划清范围：哪些已经能做，哪些还在设计中

这份文档描述一个可扩展的完整方向，当前实现先打通了模型引导和已安装连接器启用。评审时应分别看“体验是否成立”和“现阶段交付到哪里”。

用户需求 当前状态 评审时可以怎样理解
当前会话没有模型，选一个已有模型 已接入 可直接在对话卡中选择并绑定
系统还没有任何模型，连接一个模型服务 已接入 卡内有连接向导；首个模型成为全局默认，确认前需说明影响
系统已有 PubMed，当前会话未启用 已接入 主 Agent 可提出启用请求，用户在卡片中确认
确认后继续同一次研究任务 原生执行器的上述连接器流程已实现 原任务暂停并恢复，用户不用再说“继续”
用户暂时不在，低风险设置自动处理 已接入有限范围 独立授权默认关闭；当前白名单只有 PubMed，等待 30 秒后复核
API Key（服务访问密钥）失效后自动引导修复 完整通用流程待接入 已有模型向导不等于所有认证错误都能自动修复
更多工具服务（MCP）、登录授权（OAuth）、代理、超时或计算执行环境（Runner） 通用对话接入待实现 每类设置仍要定义输入、验证、影响范围和生效方式
给一个任意 API URL 或配置路径就自动接入 不属于当前能力 需要对应的协议或适配器，不能直接变成工具

本次可以证明的核心价值是：主 Agent 为研究任务请求启用 PubMed，用户确认后，同一次任务实际检索并给出结果。 不能据此声称“所有设置已支持自动配置”。

3. 走一遍：从一句检索要求到研究结果

3.1 场景的起点

假设用户已经配置好可用模型，PubMed 连接器已经安装且可用，但当前会话未启用它。用户提交：

用 PubMed 检索 3 篇 TP53 相关文献，给出标题、年份和来源。请由主 Agent 自己完成。

这里明确使用主 Agent，是为了把评审场景聚焦在对话配置链路。系统仍允许其他研究任务使用子 Agent。

3.2 系统与用户分别做什么

步骤 用户看到的内容或操作 系统需要完成的事
① 接收任务 正常的研究对话 使用现有模型开始执行
② 发现缺口 “这个检索需要启用 PubMed” 确认连接器已安装、可用，只是当前会话未启用
③ 提出变更 显示具体配置卡 记录原任务进度，在安全位置暂停
④ 用户决定 点击“确认启用并继续”或“暂不启用” 复核设置是否变化；确认才写配置，拒绝不写
⑤ 接回任务 卡片收成一行记录，任务继续 恢复原任务、提供新增工具；如果工具另需权限，再单独询问
⑥ 完成研究 返回 3 篇文献及来源 真正调用 PubMed 后再给最终答复

3.3 两个容易混淆的分支

如果 PubMed 已经启用，系统直接使用它，不重复弹配置卡。

如果用户只说“帮我打开 PubMed 工具”，这是一条单独的配置指令：系统可确定性解析目标并显示卡片，确认后结束配置操作，不凭空启动一个研究任务。带检索、分析等目标的复合任务仍由模型选择工具；当前不能保证每种表达都会触发同一种提案路径。

4. 看界面：待确认、已处理和任务结果长什么样

4.1 卡片要帮助用户做一个具体决定

一张 PubMed 配置卡应该让用户马上回答三件事：为什么要改、改什么、影响谁。示意文案如下：

启用 PubMed 文献检索

当前任务需要查询文献；PubMed 已安装，但尚未在当前会话启用。

将做的变更：把 PubMed 加入本会话的可用连接器。

影响范围：仅当前会话；其他会话不变。

下一步：确认后继续刚才的检索。若实际调用另需权限，会单独提示。

[确认启用并继续]　[暂不启用]

补齐字段和确认可以一次提交；没有新变化时不再增加同样的确认弹窗。如果后来需要改变地址、范围或验证动作，应先更新卡片，让用户看到变化后再确认。

4.2 处理后收起，但保留可查看的记录

用户确认、拒绝或请求失效后，完整操作卡退出，留下类似其他活动记录的一行：“PubMed 已启用 · 仅当前会话”。点击可以展开查看变更、作用范围、决定来源和任务状态；不再出现旧确认按钮。

这样既不会让已完成卡片一直占据对话，又能让用户回看“Agent 到底改过什么”。刷新页面后也应恢复同样的记录，不在轨迹和底部各出现一份。

4.3 配置成功不等于研究完成

状态文字 具体含义
等待配置 原任务保存了进度，正在等本次设置决定
PubMed 已启用 设置写入成功；还没有宣称已经检索
等待工具权限 设置已可用，但实际工具调用仍需按权限策略授权
任务继续/正在检索 原任务已恢复执行
研究结果 查询和整理结束，出现最终助手答复

卡片使用明确标签、可访问的字段错误和状态提示；键盘能操作、窄屏能看全范围与主按钮，中英文含义一致。不要靠一个“成功”覆盖以上所有阶段。

5. 第一次连接模型：没有 Agent 可用时怎样引导

模型是 Agent 处理任务的基础。如果系统完全没有模型，不能要求“先让 Agent 帮你配置自己”；这一入口必须由界面和后端直接提供。

5.1 页面打开时先让用户表达任务

无模型会话初始显示正常输入区，加一条轻量的“在对话中配置”入口，不自动展开大卡。用户既可主动点击，也可先输入问题再提交。提交时发现缺模型，就保留原草稿、打开同一张卡，不创建必然失败的研究任务。

卡打开时隐藏下方重复入口；关闭后入口恢复、草稿保留。没有输入任务时，配置成功不会发送空任务。切换会话不能把旧卡或旧草稿带到另一会话。

5.2 三种情况，三种结果

用户当前情况 卡片怎么做 保存后影响
已有有效默认模型 不需要卡，直接执行 沿用默认与继承关系
系统有模型，但本会话缺模型 选择已有模型，或连接另一个 绑定当前会话，不更改全局默认
系统完全没有模型 直接打开服务商连接向导，不显示空下拉框 首个模型设为全局默认，确认前说明继承它的会话也会使用

连接向导只收集服务所需的最少信息，例如协议、地址、模型和必要凭据。允许无密钥的本地端点不应被强迫填假 Key；未知模型可在用户允许后查询有限候选，或手填模型 ID。

设置首个全局默认时保留其他全局配置；当前会话已经通过继承取得该模型时，不额外制造一份会话覆盖。

5.3 不能把所有错误都叫作 Key 错误

地址不可达、超时、额度不足、模型不存在和认证失败应分别说明。连接测试成功也不自动证明模型支持图片。认证失效的通用修复、按任务能力主动换模型仍属于后续接入；修复共享服务时优先新建独立连接，避免影响别的会话。

密钥使用专用输入框直达后端凭据存储，不写进普通聊天或发给模型。外部连接测试不携带用户研究内容；可能计费的测试要在确认前说明。

6. 用户给了一个地址或路径，系统能帮到哪一步

用户常见的表达是“API 地址在这里，你帮我填一下”或“配置文件在这个路径”。设计需要把这些输入翻译成明确操作，不能把字符串直接当成可执行配置。

用户给的信息 应当怎样解释 当前是否已完整支持
受支持模型服务的 URL 在已有协议向导中填地址、验证并绑定 已有模型连接向导
已安装的 PubMed 目录项 为当前会话启用它 已支持
电脑上的配置文件 用文件选择/上传，并说明传到哪个环境 通用导入待接入
服务器上的配置路径 明确服务器、文件格式和要读取的字段，只读获准文件 待接入；不能把电脑路径当服务器路径
已保存凭据或环境变量 从有限引用中选择，后端解析 通用机制待接入
任意 HTTP 接口或以命令启动的工具（STDIO） 先有明确协议/适配器及权限设计 不因给出 URL 或命令就自动成为工具

后续路径导入不能扫描目录猜密钥或执行文件里的命令；解析符号链接后仍要遵循读取范围。代理、超时、Runner 等设置也需要逐类接入，而不是给 Agent 一个“修改所有设置”的入口。

7. 改完影响谁：把保存位置和使用范围分开讲

7.1 “服务登记在系统里”不等于“所有会话都切换”

连接一个新模型服务时，资源可以登记在部署的模型列表里；当前会话是否使用它，是另一项绑定。卡片必须分别说明这两件事。

会话通常沿用项目或全局默认值；只有自己的覆盖值存在时才优先用自己的值。这里的“继承”就是“没有单独设置时用上一级默认”，评审不需要先理解存储结构。

7.2 按具体动作说明影响

动作 用户应看到的范围说明
为已有会话选择模型 仅当前会话使用；其他会话与全局默认不变
启用已安装 PubMed 加入当前会话的连接器集合，保留其他已启用项
零模型首次连接 首个模型将成为全局默认；这是需要明示的例外
后续修改项目/全局设置 展示受影响对象，以及本会话是否仍被自己的覆盖值挡住
仅有系统级的代理/超时/网络设置 说明影响整个部署，不伪装成“只改本会话”

没有真实的单次任务覆盖能力，就不展示“仅本次运行”。历史任务和已排队任务当时已经确定的设置不能被悄悄改写；当前原生恢复只给原任务加入这次批准的连接器。

以后提供撤销时，要恢复“原来没有单独设置”的继承状态，不只是把旧显示值复制回来；也不能顺带删掉其他会话正在用的共享服务。完整通用撤销目前尚未交付。

8. 为什么确认后能接着做：任务中间保存了什么

8.1 用户感受到的是一次任务

这里的“暂停”是：系统在已经发出的工具调用完成后，记录原目标、已提交的结果和接下来继续所需的上下文，然后等待配置决定。用户确认后，系统拿这份记录接着执行，不要求用户重新描述整段问题。

工程上这份记录叫“检查点”。一次任务有自己的编号（run ID），当前原生连接器流程在暂停前后保留同一个编号；它不是恢复任意程序的内存栈，也不能自动判断所有外部动作的成败。

8.2 确认过程中，各方的职责

角色 负责什么 不由它决定什么
Agent 判断任务需要什么、提出具体配置需求、接回原目标 不能代用户批准提案
用户 看变更与范围，补缺项，确认或拒绝 不需要自己寻找设置页或拼写内部配置字段
后端配置与运行系统 校验当前条件，保存设置/记录，重建工具并恢复任务 不能只写成功文案而没有实际保存/执行

卡片必须等检查点和等待状态都保存后才能供确认。等待期间不输出“请确认后再继续”的最终助手答复；研究任务真正完成时才有最终答复。后续用户消息可以排队，但不应越过前面正在等待配置的任务。

8.3 刷新、拒绝和停止怎么处理

刷新不应使任务遗忘正在等待什么；重复确认也不能创建第二次配置或第二个研究任务。拒绝时原任务收到拒绝结果，有安全替代方案就继续，否则解释限制。点击 Stop 后，旧卡和倒计时不能再次唤醒任务。

如果 Stop 先发生，就不能继续提交旧请求；如果配置已经保存后才 Stop，应保留“已保存”的事实，同时停止任务接续，不能谎称刚才的配置从未发生。

当前同一任务恢复只覆盖“原生执行器”这套 Agent 执行后端的连接器启用。另一套后端 JiuwenSwarm 与旧历史仍走有关联的后续任务，状态需如实说明。外部操作结果未知时不能自动重做，例如重复上传、付费调用或再次提交远程作业，这类通用保障还需继续完善。

9. 用户不在时怎么办：30 秒机制到底授权了什么

9.1 先有独立授权，才有倒计时

用户可能让 Agent 跑一个长任务，人暂时离开。对非常有限的低风险设置，允许事先开启“自动应用低风险会话配置”，默认是关闭的。

当前白名单只有 PubMed。开启后，符合条件的请求提供 30 秒缓冲和取消入口；服务端到期再复核授权、连接器状态、设置是否被别人改过，以及任务是否已停止，条件仍满足才应用并接回任务。

白名单要逐项审查：公开只读、不增加凭据或费用、不修改项目/全局设置；新的连接器不会自动加入。

9.2 评审需要确认的边界

情况 行为
只开了工具的 Always allow 不因此获得配置修改权，仍需人工确认或独立配置授权
开了低风险配置授权，PubMed 满足条件 倒计时到期、复核后应用；浏览器关闭也由服务端负责计时
新连接器、模型密钥、OAuth、代理、远程执行或全局设置 不因等了 30 秒就自动获准
倒计时中取消、关闭授权、Stop 或条件失效 不自动应用，不偷偷改其他设置代替

即使自动启用了 PubMed，实际调用仍受工具权限控制。30 秒是用户已经授权后的一段取消机会，不是“沉默等于同意”。

10. 怎么避免每加一个设置就重新做一套功能

10.1 分成“公共流程”和“每类设置自己的规则”

模型、PubMed、代理需要的字段不同，但都可能经历：说明缺口 → 收集输入 → 展示影响 → 用户决定 → 验证保存 → 让任务使用新配置。这个公共流程可以复用。

各类设置仍有自己的规则。模型适配器知道怎么验证模型地址与凭据；连接器适配器知道如何启用已有目录项；代理适配器需要知道全局影响与生效方式。这些业务判断不能因为表单可复用就省略。

10.2 新增设置时，希望开发者只补什么

以未来新增“超时设置”为例，开发者应声明：哪个字段、合法范围、影响哪个环境、怎样预览/验证、何时生效。公共服务负责显示卡片、接收决定、记录变化和协调任务，不必再次写整套对话界面。

不过，当前尚未完成这个通用层。现有连接器提案、回执和恢复机制可复用；根据字段描述自动生成表单、统一维护可配置能力、接入各类设置等仍需实现。这个例子是扩展方式，不是超时已经可在对话里修改。

11. 没走通时怎么办：用几个具体问题检查设计

评审者可能问 预期处理

12. 评审怎样验：看哪些行为，而不只看卡片漂亮不漂亮

12.1 可以现场演示的一条闭环

准备真实模型、尚未启用 PubMed 的会话，以及已安装且可用的 PubMed。要求主 Agent 自己完成一次最多三篇的检索。观察：

  1. 提交的是研究任务，不是单独的“打开工具”指令。
  2. 出现说明原因和会话范围的配置卡；原任务等待，没有提前最终答复。
  3. 确认后卡片收成可展开记录；原任务继续，不要求用户重新发问题。
  4. 如有工具权限卡，允许本次检索后出现真实来源结果。

2026-10-16 使用真实 DeepSeek-V4.1-Flash 已通过该限定闭环：单次 limit: 3 的 PubMed 检索，最终回复有三篇标题、年份和链接；无子 Agent 或 shell 调用，临时数据已清理。

不限篇数的宽题曾触发约 250 篇检索后尝试寻找大工具输出，停止时尚未形成最终报告。不要把限定用例成功讲成“所有长任务和所有模型已验证”。自动应用、拒绝、重启和 Stop 也需要各自的测试证据。

Registry 必须显式注册 schema、允许范围、敏感字段、验证预算、自动应用资格、生效方式与撤销支持。新增条目不默认加入自动应用白名单。

  committedAt: string;
};
configurationWait?: boolean;
configurationResume?: {
  requestId: string;
  decision: "apply" | "dismiss";
  connectorName: string;
};

SessionRun.status 实际为 blocked，以 configurationWait 标明配置等待。configuration_wait 是等待语义，不是另一个 status 枚举值。旧 configurationContinuation、通知去重字段和旧内联检查点继续兼容读取。

4.3 目标通用请求

目标 DTO 增加 capabilityId、schema/适配器版本、revision、stateVersion、输入描述、脱敏差异、范围/影响、验证计划、previewDigest、凭据可用状态、应用结果、激活/恢复状态、错误与允许动作。

内部另存规范化计划、基线 overrides 的字段缺失信息、资源版本向量、凭据草稿引用、原任务与附件/产物引用、确认记录、验证 attempt、receipt 与恢复幂等键。

5. 存储、版本和事务

5.1 现有边界

连接器请求存于现有 catalog.sqlite 的 connector_configuration_requests，配置沿用目录/会话领域存储。run 列表仍有文件写入边界；新检查点通过 VersionStore.putRecord("ConfigurationCheckpoint", ...) 保存不可变记录并在 run 中存引用。

当前已对连接器基线、请求状态、Stop generation 和重复决定做检查/幂等。配置变化、恢复入队和通知分别持久化，尚未形成通用跨存储事务；不能声称仅因使用 SQLite 和 CAS 就获得所有步骤的 exactly-once 保障。

5.2 目标持久记录

可在同一 SQLite 连接上增加：请求和不可变 revision、验证/应用操作、加密凭据草稿、资源版本、应用 receipt、事件/恢复 outbox。请求与操作分别有唯一幂等键；活动需求按会话/能力/目标 fingerprint 去重。

原会话停止 generation 应与既有通知/停止语义协调，避免另建互不一致的计数器。草稿凭据建议空闲 30 分钟、提案最长 24 小时；这是待实现默认值，不是当前连接器 DTO 已提供的有效期。

所有设置入口，包括设置页和 provider/model 删除，都需要更新相关资源版本。版本向量覆盖目标 overrides、父级继承、provider/model、凭据 generation、连接器安装/配置与策略指纹。不得存明文凭据 hash 充当版本。

5.3 目标条件提交

TEXT
事务外完成获准验证并记录 attempt
→ 运行安全边界和写入串行边界就绪
→ 根据最新目录准备候选变化
→ 同步事务内复核 revision/digest/资源版本/Stop/授权/有效期
→ 写配置、正式凭据、版本、applied receipt 与恢复 outbox
→ COMMIT 后切换内存目录、通知并处理恢复

事务内不 await，不调用会独立保存的公共 mutator。必须提取无独立提交的内部领域操作；顺序调用 createProvider、登记模型和写绑定不能自动视为一个原子事务。写失败要恢复内存目录并保证队列可再次工作。

单进程写入是当前基线；未经验证不宣称多 API 进程可以共同写同一目录。原生恢复 outbox 应引用既有 run ID 和检查点，不通过新建后续 run 规避同一 run 语义。

6.2 目标通用扩展

通用服务需要独立卡片快照、凭据草稿、无副作用 preview、带版本的决定、单独激活/恢复重试与反向提案能力。建议新增 GET R、POST R/credentials、POST R/preview、POST R/continue 和 POST R/reversal，并对现有单数决定接口按版本扩展；这些尚非已可调用契约。

目标 preview 输入包括已注册 capability、用户字段、范围、expectedRevision 和浏览器内存中的 credential handle；决定输入包括 revision、服务端 previewDigest、批准/拒绝和精确操作。凭据不能放进模型工具参数。

写接口支持持久 Idempotency-Key：同键同规范化载荷返回同结果，同键不同载荷返回冲突；不同键也不能重复应用同一 revision。不要把此目标断言冒充当前所有专用路由都已支持该请求头。

目标 Agent 工具 inspect_configuration 和 propose_configuration 只返回脱敏状态/请求 ID；拒绝任意 HTML、密钥、headers/env、URL userinfo、通用文件写路径和自定义适配器代码。

所有用户端点校验已有鉴权、session/project 归属与可写状态。审计没有独立用户身份时记录已认证客户端，不伪造多租户隔离。目标错误至少区分非法输入、旧预览、权限不足、资源变化、停止、凭据/提案过期和幂等载荷冲突。

7. 模型引导、验证和凭据

7.1 当前引导规则

前端缺模型检查不依赖 LLM。空会话只保留轻量入口；提交非空草稿时打开卡并阻止 run 创建，确认后经正常路径只提交一次。取消保留草稿；无任务时不提交空 run。

ConversationalModelCard 复用 ModelConnectWizard。零模型直接进入连接向导，首次连接前固定并展示全局默认范围；写默认时读取并保留其他全局 overrides。已有模型时选择或新连接绑定当前会话。当前会话已通过继承取得首个模型时避免额外覆盖；并发变化应使旧绑定确认失效。

7.2 通用验证要求

连接验证按正式运行的 apiProtocol/apiVariant 生成请求，支持 provider 明确允许的 tokenOptional；不能根据 hostname 猜协议或构造伪 token。

目标验证计划包括固定、无用户数据的输入、主机与协议、有限次数、费用提示、超时与响应预算。建议连接单次默认 10 秒、响应 64 KiB，模型发现另设列表上限；这些作为统一验证器的待实现合同，不能替代对当前向导行为的单独核对。

默认不把凭据随重定向传到其他主机。模型 API 沿用模型层的外连/代理策略，不把 Runner 沙箱网络策略误当成全部 API 策略。错误分类区分认证、模型不存在、网络、额度/限流、协议和能力未知，回传有限脱敏摘要。

未知模型允许先授权有限发现，用户再选择实际结果并批准绑定；不支持发现时手填。发现授权不升级成保存授权，连接成功不证明视觉能力。外部验证已发出但结果未知时不自动重复可能计费调用。

7.3 凭据通道

TEXT
专用表单 → 后端加密草稿 → 获准验证器 → 正式凭据存储
Agent / 普通快照 / SSE / 日志：仅见 missing、provided、expired 等状态

通用草稿以请求、字段、目标、版本绑定，只在浏览器内存保留短期 handle；不得进入聊天状态、URL、持久浏览器存储或模型上下文。已有 provider 凭据只用于获准端点。正式提交后转存或清理，取消/过期清理未引用草稿，执行中的有界验证租约不能被清理器误删。

保持现有 CORS/鉴权边界，关闭敏感请求体日志，限制字段和大小。当前向导已复用后端密钥存储，但通用草稿接口、TTL、修复共享凭据和原子多资源提交尚未全部接入。

用户曾在普通消息中粘贴的凭据不因新增专用通道自动从历史消失；不在新提案或工具结果中复制明文，既存消息清理需要单独的历史管理流程。

8. 触发、去重与 Specialist 边界

独立指令预检只解析已安装连接器的 ID/显示名与完整肯定启用命令；名称不唯一、不认识、否定或复合任务返回不适用。已启用返回当前状态，未就绪返回不可用；其他普通任务继续走正常 Agent 流程。

独立指令请求用 user-request:* 区分，不对应研究 run，不生成 continuation。已有 applied 记录不能作为“仍启用”的判断依据，必须读取当前 effective 设置。待确认请求按会话和连接器复用。

主 Agent 的研究任务通过 propose_connector_enable 提案；不要把该模型工具路径描述为所有复合自然语言需求的确定性识别。专用工具仅提供给主 Agent，参数与目录由服务端校验。

Specialist 的现有预设连接器仍可与会话设置组合；本功能不改变该授权/装配规则。当前子 Agent 没有通用提案工具。未来如增加，所有提案仍需服务端归属、去重、决定与恢复协调，不能并行卡片各自覆盖设置。测试主 Agent 路径应禁用委派，另测 Specialist 既有路径。

9. 原生执行器持久暂停与同 run 恢复

9.1 暂停顺序

  1. 创建持久连接器请求，提案工具返回 pending 结果。
  2. 运行时的 suspendAfterTurn 在完整工具批次结束后交回控制，不依赖模型口头承诺停止。现有生命周期记录和工具结果应先提交。
  3. 关闭模型历史中的 assistant/tool-call 配对，通过 CAS 写不可变 ConfigurationCheckpoint，含 requestId、history、Stop generation 和 committedAt。
  4. run 写入匹配引用与 configurationWait=true，由调度器映射为非终态 blocked。
  5. 列表接口确认 run/检查点就绪后才暴露待确认卡。此分支不写最终助手答复、不发 run.completed、不填完成时间。

等待不持有模型请求或长期 Promise，不依赖 SSE 连接。普通工具权限 blocked 必须与 configurationWait 区分。工具批次未完成时不能提前把配置当作已经生效。

9.2 恢复顺序

  1. 人工或获准自动决定经同一服务复核请求、会话、基线、连接器与 generation。
  2. 记录决定；确认时更新会话配置，并只把获批准连接器合入原 run 的冻结快照。拒绝不写连接器。
  3. 原 run 持久标记 configurationResume 并重新入队，保留原 ID、原始 userMessageId、事件流与检查点。
  4. 调度器在领取前复核决定状态、检查点关联和 generation；重建工具注册表，读取检查点历史并校验其 requestId/generation。
  5. 通过可信内部上下文明确告知批准/拒绝结果和原任务继续语义。旧工具结果中的“待确认”是历史，不能让模型重新等待同一卡。
  6. 从未完成位置继续；不重复创建用户原始提问，不重放已提交工具。最终答复只在原任务真正结束时生成。

原 run 恢复重新入队是执行状态变化，不是新的研究任务。恢复后的 run.started 事件也不能按“新用户问题”另插一组重复轨迹。

9.3 尚未完成的通用保障

现有 checkpoint 以模型历史为核心，并不等于已实现所有外部动作/产物的提交协议。通用协调器还应明确记录已完成动作、产物和附件引用、资源依赖版本、恢复位置与不确定外部提交。

未知副作用先查权威状态，否则需要用户处理；不能猜测成功、重新上传、重新付费或重复提交远程作业。冻结模型 ID 也不自动冻结共享 provider 地址与密钥依赖，跨类型恢复需增加依赖版本检查。

10. 决定、并发、队列与兼容

当前连接器应用检查会话可写、请求 pending、基线连接器集合匹配、连接器就绪与插件允许、Stop generation 有效。并发配置变化不能用旧完整数组覆盖；请求变 stale 时不写配置。重复决定返回既有结果，不重复恢复。

人工/到期决定、Stop 与配置写入须在明确写屏障里排序。后续用户消息可入队，不能使原配置请求的 generation 意外失效，也不能越过前面的配置等待 run。无关 queued run 的取消不能等价为整个会话 Stop。

Stop 先发生则禁止应用/恢复；提交先发生则保留 applied 事实，Stop 抑制恢复。会话归档/删除同样阻断旧请求。任务恢复领取前再检查，不仅在点击决定时检查。

JiuwenSwarm 与旧 configurationContinuation 继续使用有关联的后续 run；该分支沿用历史去重和来源校验，不迁移或篡改成同一 run。原生新请求不通过创建关联任务来伪装暂停。已失败模型 run 保持失败，未来修复不能追溯改其历史状态。

目标通用服务用持久应用回执与恢复 outbox 统一跨存储重试：原生 outbox 指向原 run，旧兼容路径需要新 run 时预分配候选 ID、在同一 run 文件写屏障幂等查找/创建。服务内部旧函数名包含 continuation 不意味着原生路径一定新建 run，应以持久 ID 核对。

11. 低风险自动应用与服务恢复

当前会话字段 autoApplyLowRiskConfiguration 独立于 approvalMode，默认 false。isAutoApplicableConnector 当前仅允许 PubMed，服务端控制资格，模型不能新增白名单。

提案时授权和白名单满足则记录 autoApplyAt=createdAt+30s。前端倒计时只展示；到期由服务端检查授权、基线、连接器/插件、会话、Stop generation 和任务状态，经同一决定服务应用并恢复。浏览器关闭不能取消服务端既有授权，进程重启应恢复未决计时。

关闭授权应清除/抑制到期操作，使请求回到人工确认。到期与人工确认只有一个结果，重复扫描读取已有状态。拒绝、取消、Stop 或前提失效均阻止自动应用。启用后的工具仍按自身权限策略执行。

中断窗口 恢复要求
工具批次未结束、检查点未提交 不开放确认；核查实际执行状态，不重放未知动作
检查点与 blocked 已提交、尚未决定 恢复同一 run 与待确认卡
已应用、恢复尚未入队 依据持久决定和匹配检查点幂等补齐恢复；通用 outbox 仍待加强
原 run 已 queued/running/terminal 关联原 ID，不另建第二个任务或重复执行
外部验证发出而结果未知 不自动重发，标明未知并等待明确处理
Stop 发生、旧到期操作再次被领取 generation 校验失败，不唤醒

普通崩溃中的 running/工具权限等待保留各自恢复策略，不能把所有 blocked 都当成配置暂停。重启支持与自动到期都需独立故障测试，不能只根据人工确认真实用例推定通过。

12. 前端、事件与设置同步

卡片展示按 session/run/request 绑定，决定前恢复实体快照，运行过程继续使用既有事件流。当前实现不能假设已经有全部通用 configuration.required/updated/resolved 事件；这些可作为后续带 revision/stateVersion 的 DTO 事件设计。

状态 展示与动作
无模型、未打开卡 轻量入口；可输入草稿

决定后隐藏可操作卡并归位到原 run，避免同时在历史和底部显示重复回执。展开状态 key 使用 request 稳定 ID。回执不能替代权限，也不能把已应用错误标为任务已完成。

异步请求捕获 sessionId/requestId，SSE 核对 session/run，再更新当前视图。会话切换不得混入旧卡、旧工具输出或文件。设置提交后通过既有加载入口刷新模型列表、会话设置和来源；避免设置页与对话显示两份状态。

目标事件与普通 DTO 一样脱敏，用 ID/version 去重；刷新以快照补齐，SSE 重放不能重新调用决定接口。表单 label、错误提示、状态播报、键盘展开、窄屏与 i18n 纳入验收。

13. 撤销、迁移、上线与回退

通用撤销创建反向提案，复核资源版本并恢复原字段缺失/继承；默认只撤销绑定，保留新建共享资源。已被引用资源不因一次撤销删除。外部验证、已发送请求和业务动作不能撤销。当前没有完整通用撤销服务。

迁移采用新增表/可选字段与独立 schema 版本；不占用未经核对的全库版本号，不整体重写旧 run/事件。旧检查点和关联后续记录继续可读，历史语义不被篡改。

完整框架可另设发布开关，但该开关及默认值必须真实实现后才写入部署合同。关闭新增功能时应仍能读历史、取消等待和清理草稿，不能隐式回滚已保存配置。

2. 卡片什么时候出现

进入空会话不会自动展开完整配置卡。模型缺失时保留输入区的手动配置入口，用户提交需要模型的任务后再按需引导。

连接器有两条入口：

  1. 独立启用指令，例如“帮我打开 PubMed 工具”：浏览器调用服务端配置预检，解析已安装目录中的唯一目标。它直接创建待确认提案，不需要先跑 LLM，也不创建没有研究目标的后续任务。已启用时返回当前状态。
  2. 研究任务中的需求：主 Agent 判断需要未启用连接器时，调用 propose_connector_enable。复合研究请求不走上述简单指令解析；是否提出配置请求仍与模型的工具选择有关。

子 Agent / Specialist 可以按既有规则获得自己的预设连接器。主 Agent 也可能选择委派任务；因此，没有配置卡不能单凭现象判定为识别失败，还要检查具体由谁调用了什么工具。要单独验证主 Agent 的配置链路，应明确要求不使用子 Agent。当前提案工具只提供给主 Agent，未实现所有子 Agent 共用的配置提案机制。

3. 确认之后怎样继续

原生执行器的连接器流程为：

  1. 主 Agent 提案；运行时在当前工具批次完成后保存模型历史检查点。
  2. 原 run 进入非终态的 blocked/configuration_wait；检查点提交后才显示可确认卡片。此时不写最终助手答复。
  3. 用户确认后，只把获批准的连接器加入该 run 的设置快照，重新装配工具，从同一 run 的检查点继续。无需再发“继续”。拒绝结果也交回原 run，由 Agent 选择替代路径或说明限制。
  4. 已处理卡片默认折叠为一行可展开的只读回执，例如“PubMed 已启用 · 仅当前会话”。点击可查看详情，不重复显示确认按钮。
  5. 连接器调用若另需授权，会出现独立的工具权限卡；允许后继续。配置已保存、工具已获授权、任务已完成是三个不同状态。

Stop 可终止等待并阻止旧请求唤醒任务。重复确认不会创建第二个任务。JiuwenSwarm 和旧记录仍采用关联后续 run 的方式，不能把它们描述为已经支持同一 run 暂停恢复。

4. 长任务与 30 秒自动应用

“Always allow”是工具权限设置，不自动授予配置修改权。会话中另有默认关闭的“自动应用低风险会话配置”授权。

当前只有已安装、就绪且满足检查条件的 PubMed 请求属于白名单。开启独立授权后，卡片提供 30 秒缓冲和取消入口；到期由服务端复核授权、设置基线、连接器状态及任务/Stop 状态，再应用并恢复任务。关闭授权、取消或条件失效会阻止自动应用。

模型连接、密钥、OAuth、全局设置等不能因等待 30 秒就自动获准。30 秒机制已接入当前切片，但不属于下述人工确认真实模型用例的实测结论。

1. 产品目标与原则

把“找到设置、理解字段、填写保存、回到任务”变成“Agent 说明需要调整什么 → 用户在对话中补充或确认 → 系统验证、应用 → 原任务继续”。

  1. 优先沿用有效默认值与继承关系。配置能完成任务就直接执行，不为展示功能人为清空设置，也不为轻微优化频繁打断。
  2. 配置卡只在用户主动要求、必要能力缺失或确实阻塞任务时出现；设置页继续承担集中维护和手动覆盖。
  3. Agent 负责检查需求和提出建议；可信后端负责字段校验、凭据存储、权限与范围检查、提交和激活。Agent 不能批准自己的提案。
  4. 一张卡聚焦一个配置目标，预填可确定的信息，只要求用户补缺项。资源保存位置、使用范围、目标地址和关键变化必须直接可见。
  5. 配置已保存、配置对任务生效、任务已继续是三个独立结果，界面分别反馈。连接器启用和工具执行权限也是两次独立决定。
  6. 原生执行器支持的连接器配置应在原任务中暂停和恢复；配置等待不能先写一条最终答复，再要求用户重新发送任务。

3. 入口、默认行为与子 Agent

3.1 打开会话

已有可继承的默认模型时直接使用，不出现缺模型卡。无模型会话也先显示普通输入区，不自动插入完整配置卡。

无模型时，输入框下保留轻量提示及“在对话中配置”入口。点击可主动打开卡片；用户也可先输入任务，提交非空内容时确定性检查模型，缺失则保留草稿、打开同一张卡，不创建必然失败的 run。

卡片打开时隐藏手动入口，避免重复；关闭后入口恢复。未输入任务时确认模型不会提交空任务。切换会话、归档或原会话已有新模型时，不能把旧卡片显示到另一会话。

3.2 独立配置指令

“帮我打开 PubMed 工具”“请在当前会话启用 PubMed”等独立、无歧义指令，由后端根据已安装目录确定目标，不依赖 LLM 选中工具。已启用则返回当前状态；未就绪则说明原因；已安装且就绪则创建待确认提案。

此类指令没有研究任务，确认后不启动无目标运行。相同会话与连接器的待确认请求复用；历史已应用请求不能代表当前仍启用，后来关闭后允许提出新请求。

否定句、仅讨论连接器、包含其他目标的复合研究任务不由简单启用指令解析器猜测。

3.3 执行中的需求

研究任务仍由 Agent 判断工具需求。主 Agent 发现缺少已安装连接器时，调用受控提案工具；系统在安全边界保存检查点，再展示可确认卡片。目前复合任务的提案仍取决于模型工具选择，不能宣称任意说法都能确定性识别。

子 Agent / Specialist 保留既有预设连接器和工具装配规则。用户允许子 Agent 使用自己的设置，不因本功能强制把子 Agent 的连接器收窄成主会话列表。当前配置提案工具仅提供给主 Agent；是否扩展子 Agent 提案需另行接入统一决策机制，不能暗示已经具备。

主 Agent 委派给已具备 PubMed 的 Specialist 时，可能直接出现工具权限流程而无主 Agent 配置卡。验证主 Agent 配置链路时应明确要求不委派子 Agent，不能仅凭“没有卡片”判断失败。

4. 配置卡与处理后的回执

4.1 待确认卡

卡片直接展示：任务原因、将执行的变化、关键字段及最少输入、旧值与新值、资源保存位置、使用范围、验证目标与可能费用、任务当前状态。

主要动作是“确认配置并继续”和“暂不配置”；高级设置折叠。无输入的已有资源选择也使用同一交互。用户填写完整预览后可一次提交，不增加内容相同的二次确认弹窗。后续若目标地址、范围或动作实质变化，必须更新预览再确认。

正在完成当前工具步骤时说明“等待当前步骤完成”；检查点未提交前不能开放实际配置决定。验证失败在原卡定位错误，不丢输入、不替换已有有效设置。

4.2 已处理回执

确认、自动应用、拒绝或失效后，完整可操作卡片退出，保留与其他活动记录一致的一行只读、可展开回执，例如“PubMed 已启用 · 仅当前会话”。

点击、Enter 或 Space 可展开查看配置、范围、决定来源与任务接续状态，再次操作可收起。不保留旧确认按钮；原生流程的记录位于同一 run 轨迹，旧关联 run 记录继续按历史语义显示。刷新后从持久请求恢复，不能在底部重复显示已处理卡。

4.3 可访问性

输入有明确 label，字段错误可访问，阶段变化有状态提示。键盘可完成操作；窄屏纵向显示，范围和主动作始终可见。中英文使用统一文案。配置等待、工具权限等待、排队和最终完成必须有不同状态。

5. 模型选择、连接与凭据

5.1 首个模型

系统完全没有登记模型时，卡片直接提供服务商连接向导，不显示空的模型下拉框。确认前明确说明：首个模型成为全局默认，当前及以后继承该默认值的会话会使用它。写默认值保留其他全局覆盖字段。

连接成功后当前会话若已通过继承取得所选模型，不额外写会话覆盖；旧卡片若与其他窗口后来选择的模型冲突，应判为过期。用户原任务通过正常提交路径只发送一次。

5.2 已有模型和新连接

已有登记模型但当前会话缺模型时，优先选择已有模型；也可连接另一个。此时绑定范围为当前会话，不改变全局默认。资源保存在部署的模型列表，与“在哪个会话使用”分别展示。

仅支持既有协议和提供方预设。服务允许无密钥时不强迫填写伪 API Key。协议、地址或模型不明时不得编造：可以在授权后进行有限模型发现；不支持发现时允许手动模型 ID，并说明验证结果。

5.3 后续凭据修复与能力诊断

模型认证失效时，目标是由确定性错误分类打开专用修复入口，不依赖失效 LLM；超时、限流、额度不足不能统一归为密钥错误。当前尚未完整接入该通用修复流程。

修复优先建立独立连接并重新绑定，避免改共享 provider 密钥影响其他会话。连接测试使用固定、无用户任务内容的最小请求；可能计费时先说明。连接可用与视觉等能力已验证分别记录，文本测试成功不能自动证明视觉能力。

密钥只经专用表单到后端加密存储，不进入普通聊天、模型输入、SSE、工具轨迹或日志。取消时清理未引用的凭据草稿；已有凭据不能因模型建议新地址而转送给未确认主机。

没有真实 run 级覆盖时，不显示“只用于本次运行”。当前会话设置通常影响之后的运行；历史和其他排队运行的冻结快照不应被暗改。原生配置恢复仅在原 run 的冻结快照上合入获批准的连接器。

撤销会话覆盖要恢复字段缺失/继承，不简单复制旧 effective 值。改父级但会话覆盖仍在时，不得声称当前任务已切换；需要明确附加会话变化或改选会话范围。

8. 原任务暂停、恢复与异常

8.1 原生执行器连接器流程

TEXT
执行原任务 → 主 Agent 提案 → 当前工具批次结束 → 提交持久检查点
→ 原 run 等待配置 → 人工决定/获准自动应用 → 原 run 重新入队
→ 注入决定并重建工具 → 从检查点继续 → 原任务最终答复

等待是非终态，不写 finishedAt，不发提前完成事件，不先输出“请确认后继续”的最终助手消息。确认后保留 run ID 和原始用户消息，工具已提交结果不重放。等待不靠浏览器连接或内存 Promise 维持；重启后仍读取持久状态。

确认时只应用该提案允许的变化；拒绝时向同一 run 传递拒绝结果，有安全替代路径则继续，否则说明限制并结束。用户无需再发“继续”。后续新消息可排队，不应越过前面等待配置的原任务。

8.2 工具权限、停止与重试

启用连接器不批准检索、代码、网络或其他工具调用。恢复后若出现工具权限卡，原 run 转入对应等待，授权后再继续。

Stop、归档和删除可以终止配置等待并阻止旧请求唤醒任务。取消先于提交则不应用；提交先于停止则如实保留已保存结果，抑制接续。重复确认、页面刷新和到期/人工决定竞态不得产生第二次应用或第二个任务。

配置成功但恢复未开始时显示“已保存，等待接续/处理问题”，不能声称任务完成。恢复重试只重试恢复步骤，不重复验证和写入配置。

8.3 兼容与当前限制

JiuwenSwarm 与旧关联记录仍使用关联后续 run，不能把历史伪装成同一 run。已失败的旧 run 保留其终态；未来模型修复后需要有来源的恢复策略，不能追溯改写失败历史。

未知外部副作用不能猜测成功或自动重放，应查询权威状态或交给用户处理。当前切片尚无覆盖全部外部副作用的通用 outbox/不确定提交协议；本设计要求不等于已经证明所有长任务均可安全恢复。

9. 长任务的低风险自动应用

“Always allow”属于工具权限；配置另有默认关闭的“自动应用低风险会话配置”授权。界面说明白名单、仅会话生效、30 秒缓冲、取消和关闭入口，并记录授权变化。

当前白名单只有 PubMed。新连接器默认不在白名单；服务端逐项审查已安装、就绪、公开只读、无需新增凭据和付费等条件，不能接受模型提交 lowRisk=true 作为授权。

满足条件的请求显示 30 秒倒计时。到期由服务端重新检查会话授权、设置基线、Stop generation、连接器状态和任务状态，再通过与人工确认相同的提交与恢复路径执行。浏览器关闭不影响已授权调度；关闭授权、取消、Stop 或条件失效则阻止自动应用。

30 秒是事先授权后的撤销机会，不是授权本身。模型连接、凭据、OAuth、代理、远程执行及全局/项目设置仍需人工确认。自动启用也不放宽实际工具执行权限。

10. 通用配置架构与扩展方式

此节是公共机制的目标设计，目前尚未完整提取成通用服务。目标是让新设置类型接入有限接口，复用卡片、决策、提交和恢复，同时保留领域校验。

要求 ID 公共机制 适配器责任
CFG-01 能力目录与脱敏检查 声明字段、缺项、允许范围、风险、生效时机和版本
CFG-02 结构化提案及去重 生成规范化计划、差异、诊断依据与验证计划
CFG-03 用户输入和决定通道 标记敏感字段；用户确认绑定精确版本和目标
CFG-04 验证、条件提交与反向变更 按领域验证；应用失败不破坏有效配置；撤销检查版本
CFG-05 安全边界、检查点和激活 声明能否同一 run 恢复、仅后续生效或需重启

新增同类的“启用已安装连接器”可复用现有链路。新增密钥、代理或 Runner 等不同设置，仍需注册领域适配器并验证权限、作用范围与激活；不是给任意字段开放通用 JSON Patch。

目标 Agent 工具是脱敏的 inspect_configuration 和仅提案的 propose_configuration；目前实际接入的仍是专用 propose_connector_enable。用户决定端点不能成为 Agent 工具，模型生成的任意 HTML、命令或路径不能变成配置表单/写入操作。

11. 状态、并发、凭据和撤销保障

当前连接器请求状态为 awaiting_confirmation / applied / dismissed / stale；run 状态与配置状态分开。通用框架还需要收集输入、验证、应用、修正、失败、取消、过期等状态，不应把目标 DTO 当成现有接口。

用户确认绑定提案版本、变更、目标主机、范围和验证动作。输入、目标或源配置变化应使旧预览失效；禁止用旧全量对象覆盖其他窗口后来设置的值。所有设置入口将来需共用资源版本边界，而不只检查新卡片的版本。

验证发生在正式提交前，外部请求不占数据库锁。配置、应用回执和恢复意图应通过事务/outbox 协调；当前跨 SQLite 与 run 文件的通用事务保障仍是后续工作。结果不明时先查回执，不能盲目重试可能计费或产生副作用的动作。

目标撤销流程创建反向提案、展示差异再确认；保留继承信息，不覆盖后续修改，不顺带删除被其他会话引用的共享资源。通用撤销入口尚未完成，不能把“可手工改回”宣传为完整撤销机制。

凭据使用后端加密和最小可见性。通用凭据草稿需要 TTL、请求/字段/目标绑定及清理；原始值和内部引用不得进入 Agent/普通 DTO/事件。代理认证 URL 等已有接口结果也须按字段投影，不能直接传给模型。

12. 完整验收标准

文档说明

本版修订无人值守接续设计 v7的“关联后续运行”要求，并延续可展开回执 v9的展示规则。v7 的实现能自动继续目标，但会先结束原 run、写出一条助手回复，再启动另一个 run；用户看到的是对话被打断。原 run 暂停恢复已在原生 Agent 执行器中实现，交付范围与剩余限制见集成切片 v8。

用户可见行为

  1. Agent 在执行原任务时发现需要调整配置，先完成已经发出的工具调用，在安全边界保存检查点，然后让原 run进入“等待配置”状态。此时只出现待确认卡片和运行中的暂停状态，不输出“请确认后再继续”之类的最终助手答复，也不将原任务标记为完成或中断。
  2. 用户确认，或低风险请求依已有独立授权到期自动应用后，配置生效，同一个 run从检查点继续。Agent 能看到确认结果和新增的可用工具，继续原目标；用户不需要再输入提示词。最终助手答复只在任务真正结束时出现一次。
  3. 用户拒绝时，原 run 收到拒绝结果；若存在安全的替代路径则继续，否则明确说明无法完成并结束。Stop generation、归档或删除可以终止等待中的任务，并阻止之后的确认或自动应用唤醒它。
  4. 确认后的卡片按 v9 折叠为一行可展开记录，位于同一任务的活动轨迹中。展开可看配置、作用范围和决策来源。额外的工具权限仍由独立权限卡决定，不因为连接器启用而自动放行。

恢复语义

  • 暂停必须是持久检查点，不靠内存中悬挂的 Promise、浏览器连接或重发原始提示词维持。等待期间不占用 Agent 执行资源；服务重启后仍显示同一个 run 等待配置。
  • 检查点记录模型上下文、已提交的工具结果及产物、待恢复位置、冻结的原设置、配置请求 ID 和 Stop generation。恢复时只加入获批准的设置变更，并重新构建可用工具。已完成的外部动作不得重放；结果不明的动作进入需要用户处理状态。
  • 配置提交与恢复意图须持久、幂等。重复确认、倒计时与人工确认竞态、页面刷新或服务重启，均不能创建第二个任务、重复执行工具或产生第二条最终答复。
  • 旧版已经产生的“源 run + 关联 run”记录保持可读；新请求使用同一 run 的暂停恢复协议，不在历史记录上伪造连续性。

验收场景

  1. 提问“先用 PubMed 查找论文，再总结”：Agent 请求启用 PubMed 时，同一 run 显示等待配置，没有最终答复；确认后同一 run 调用 PubMed 并输出总结。会话里只有一条用户原始提问和一条最终助手答复。
  2. 等待配置时刷新页面或重启 API，卡片和 run ID 不变；确认后继续。重复确认不会再次调用已完成的工具。
  3. 独立低风险授权开启时，30 秒到期自动应用并恢复同一 run；关闭授权、拒绝、Stop、设置基线变化或连接器失效时不自动恢复。
  4. 确认后如工具另需权限，原 run 转入相应权限等待；授权后继续，拒绝后按工具失败处理。配置确认与工具权限是两次独立决定。
  5. 人工拒绝时 Agent 使用可行替代方案，或给出明确的受限结果；不能静默结束，也不能无条件重启整个任务。

状态与持久记录

  • SessionRun 增加明确的配置等待原因和检查点引用；blocked/configuration_wait 是非终态，不能写 finishedAt 或发 run.completed。用户原始消息 ID 和 run ID 在恢复前后保持不变。
  • 在 Agent 的工具批次完成且轨迹、工具结果、工作区版本均提交后，写入不可变检查点。内容含闭合的模型历史、已完成调用 ID、已提交产物引用、当前执行位置、原设置快照、配置请求 ID 和 Stop generation。写入检查点后才发布可确认卡片；若写入失败，不能把任务显示为可安全恢复。
  • 若运行时尚无可挂起的工具批次边界，应为配置请求添加明确的 suspend 控制结果，并在编排层停止继续采样。不能依赖模型遵守“请停下”的自然语言指令，也不能先把“等待确认”写成普通最终回复。

决策与恢复

  1. 决策服务复核请求、会话、连接器就绪、配置基线、Stop generation 和检查点完整性。配置变更与“恢复原 run”的意图使用事务/outbox 协调；恢复操作以请求 ID 和检查点版本作为幂等键。
  2. 调度器将该 run 从 blocked/configuration_wait 变为 queued，保留其原 ID、原用户消息和事件流。恢复时读取检查点，注入可信的配置决定结果，以旧快照为基线加入且仅加入获批准的连接器，重新构建工具注册表，然后从未完成位置执行。
  3. 完成过的工具调用不得重放；若外部副作用的提交结果不能证明，转为 needs_user_action，不能猜测成功或自动重试。拒绝决定也走同一检查点恢复通道，把拒绝结果交给 Agent 选择安全替代路径。
  4. 服务启动时只恢复已持久化的配置等待和恢复意图；普通崩溃中的 running/权限等待仍按各自恢复策略处理。旧 configurationContinuation 记录继续按旧协议展示，不迁移成新 run。

服务器上的配置文件 显示具体服务器/运行环境，指定文件格式及读取字段；经确认只读取那个文件。
浏览器所在电脑的文件 使用选择文件/上传入口。用户电脑路径不能直接当成服务器路径。
环境变量或已保存凭据 展示受支持的引用选择，后端解析，模型只见不透明引用与是否可用。

路径导入作为后续扩展，逐个支持格式；不扫描目录猜测凭据，不执行文件里的命令。解析路径与符号链接后仍须遵循对应部署的读取范围，结果仅保留需要的字段。

3.5 首次启动、模型不可用

如果完全没有可用模型，Agent 无法先对话再帮助配置。因此由前端和后端确定性检查在对话入口渲染同一种配置卡，不依赖模型生成。用户的首条任务以草稿保留，配置成功后再创建运行。

模型在运行中返回认证失败时，也可由结构化错误触发卡片；不能依赖已失效模型再次输出修复建议。额度不足、网络超时等应分别呈现，不把所有失败推断成 API Key 错误。

4. 默认值与作用范围

设置种类 默认处理
已有有效配置 沿用当前有效值及来源，不自动覆写。
能支持会话级覆盖的模型/连接器选择 首选当前会话；用户明确选择时可保存到项目/全局。
提供方、MCP 服务、凭据等共享资源 如实显示“保存到本部署资源列表”，再单独说明在哪些会话使用；不可标成“仅当前会话保存”。
当前只有系统级的超时、代理、网络策略 卡片明确影响整个部署；首版不伪造会话级能力，也不因任务受阻静默修改。
端口、存储根目录、启动环境变量、宿主执行入口 不纳入首版对话写配置。后续只有专用适配器和明确生效/重启说明后才开放。

“只用于这次运行”若没有真实的 run 级覆盖，应不显示这个选项；首版“当前会话”影响该会话之后的运行，直到用户修改或恢复继承。撤销会话覆盖应恢复 inherit，不能简单复制旧 effective 值。

选项目/全局范围时还要预览当前会话的最终有效值：如果会话已有独立覆盖，修改父级不会解决当前任务。此时明确展示“同时更新当前会话”的附加变更并一起确认，或改选当前会话；不能保存了父级设置就宣称当前任务已切换。

5. 技术方案（建议新增，非现有接口）

CFG-01 配置能力目录与诊断

每个适配器声明：capabilityId、字段类型、必填项、可用默认、允许作用域、敏感字段、读取/预览/验证/应用/撤销能力、生效时机、版本标识和诊断代码。Agent 只读取当前相关能力与脱敏状态。

诊断示例：MODEL_MISSING、CREDENTIAL_REQUIRED、MODEL_CAPABILITY_MISMATCH、CONNECTOR_NOT_ENABLED。HTTP 401 等需要结合调用层和端点归因；不让模型自由改写错误分类。配置建议必须有任务需要、用户请求或可核查诊断依据。

CFG-02 结构化提案

建议主 Agent 工具：inspect_configuration（只读、脱敏）、propose_configuration（仅建立提案）。子 Agent 返回配置需求，由主 Agent 合并提出，避免并行卡片争抢设置。

提案最少保存：

TEXT
id, revision, projectId, sessionId, runId?, toolCallId?
capabilityId, reasonCode, reason, targetResourceId?, targetScope
baseResourceVersions, proposedOperations, redactedDiff
inputSchema, requiredInputs, secretRefs
verificationPlan, activationMode, continuationPolicy
state, createdAt, expiresAt?, decidedAt?, appliedAt?
verificationResult?, appliedResourceVersions?, continuedRunId?

上述 secretRefs 只存不透明引用，不进入普通工具返回。服务端根据白名单 schema 产生表单和变更摘要，不采用模型提供的任意 HTML、代码或写入路径。

CFG-03 输入、确认与凭据

新增用户专用的输入/决策接口；复用现有鉴权边界，校验会话可写性及配置范围。它不作为 Agent 工具暴露。allow_matching、Agent 自己返回的“用户同意”、其他工具的已有授权均不能批准配置提案。

密钥用专用字段提交到后端，引用现有加密机制；未应用提案使用有期限的加密草稿存储。原始值不得进入聊天消息、SSE、模型上下文、工具参数回放、普通日志和浏览器持久存储。取消/过期删除未引用的草稿凭据。已有代理等设置接口可能返回完整认证 URL，不能原样交给 Agent；必须逐字段构建脱敏视图。

建议接口形状：

  • GET /api/sessions/:id/configuration-requests：读取脱敏卡片快照，支持刷新恢复。
  • POST /api/sessions/:id/configuration-requests/:requestId/preview：接收用户补充字段，返回确定性预览，不启用配置。
  • POST /api/sessions/:id/configuration-requests/:requestId/decisions：提交 revision、预览摘要标识和确认/拒绝，以及 apply-only 或 apply-and-continue 意图。
  • 凭据使用独立输入端点生成草稿引用；具体路由与 TTL 在实现设计中固定。

用户编辑字段会生成新的提案 revision；确认只绑定用户看到的那版内容。源配置变更导致预览过期时，重新展示差异并确认，不覆盖他人后来的修改。

CFG-04 验证、提交与撤销

格式检查和配置预览可以在本地完成。带凭据的外部测试、读取用户文件或任何会产生请求的探测，需要用户在卡片明确授权；URL 重定向不得把凭据转送到未确认主机。遵循现有网络策略，允许经政策允许的本地模型服务，不把内网一律禁用。

应用顺序：字段检查 → 预期资源版本校验 → 执行已展示的最小验证 → 再校验版本 → 提交配置及审计 → 激活/接续。对连接类配置，验证失败默认不替换有效配置；可另行保存为未启用草稿，不能显示为配置成功。

首版只接入能完整回滚或原子提交的适配器。新建 provider/model/会话绑定作为一个逻辑提交：外部测试不持有数据库锁；正式绑定必须全成或全不成，未完成资源留在明确的草稿区。外部副作用不可用数据库回滚假装撤销成功。

成功记录提供“撤销本次配置”入口：再次预览反向变更并确认，用版本校验避免覆盖后续修改。撤销绑定不自动删除已被其他会话引用的新资源；凭据恢复只在后端保留策略允许时进行，否则请用户重新输入。撤销不撤回已经发送的外部请求。

CFG-05 任务等待与接续

配置等待沿用 blocked 的呈现与外部等待计时机制，增加结构化等待原因。SSE 新增 configuration.required、configuration.updated、configuration.resolved，事件与快照均脱敏并绑定 session/run/request/revision。

首版对模型与工具集合变化采用关联后续运行。 用户界面表现为“配置完成，继续任务”；系统内部在安全边界结束旧执行，保留原配置快照，并创建带新快照、continuedFromRunId 和配置提案引用的后续运行。该字段为拟新增；不能把普通失败重试字段直接当作已具备接续语义。

旧运行可沿用 interrupted 并增加明确 reasonCode=configuration_changed，前端显示“已转入后续运行”，不显示成崩溃。此语义扩展与现有恢复逻辑需要一起实现和测试。应用成功却未创建后续运行时，显示“配置已保存，任务尚未继续”，提供单独重试接续按钮。

接续载荷引用原始用户目标、已完成步骤、产物和最后一个安全等待点；不复制包含凭据的输入，也不让用户重发整段问题。它是保留进度的后续运行，不承诺恢复任意代码栈。先等待/中止并确认并行任务的实际状态，未知状态不可自动重放；已执行的上传、付费请求和远程作业必须去重或查询，不得从头执行。

当前任务未启动时直接用新配置创建首个运行。与当前快照无关且适配器明确支持的变更可继续原运行；首版不实现任意热切换。其他运行和已经排队的快照不被暗中改写。

CFG-06 状态、幂等与恢复

主要状态：

TEXT
collecting_input → awaiting_confirmation → validating → applying → applied
                         ↓                 ↓            ↓
                    dismissed          needs_fix     failed

另有 stale、cancelled、expired。修正产生新 revision，再次确认。配置状态和接续状态分开记录；applied 不等于任务已经继续。

  • 同一需求重复触发合并到原卡；已拒绝的相同提案在当前任务内抑制自动再询问。
  • 应用与创建后续运行分别使用持久幂等键；重复点击、SSE 重放、断网重试不产生重复资源或运行。
  • 刷新页面通过实体快照恢复卡片，不仅依赖 SSE。
  • 取消先于提交则不应用；提交先于取消则如实显示已保存，并抑制任务接续。提供撤销入口，不假装配置未写入。
  • 服务重启后核查提交和接续记录再恢复；绝不因为看见一条旧 pending 事件就再次写配置。

6. 首版范围

阶段 交付
首版 通用提案/卡片/诊断；已有模型选择；支持协议内添加模型 API、补充凭据、测试并绑定会话；启用已安装且已配置的连接器；无模型启动配置；刷新恢复与关联后续运行。
第二阶段 HTTP/SSE MCP 新连接与 OAuth；代理与超时等全局项；受控文件/环境变量导入；逐项补充影响预览和验证适配器。
后续独立评估 STDIO 命令启动、宿主资源、需重启的部署设置，以及新增任意 REST API 适配器。

首版不更改默认权限策略。配置连接器成功后，实际工具调用仍受原有执行授权规则约束；卡片说明后续可能需要的实际调用授权，不能用配置确认代替执行权限。

8. 本版建议的评审结论

建议采用「对话内嵌卡片 + 缺什么补什么 + 一次明确确认 + 自动接续」，首版保持现有默认值，优先补齐模型/API 和已有连接器的流程。模型 API 的新增资源默认可在本部署管理，但使用默认限制在当前会话；全局默认需用户明确选择。

交互演示仅用于评审添加 API、切换模型、成功/失败及暂不配置状态；演示不连接真实服务，不保存实际配置，也不应输入真实密钥。

用户以默认设置开始任务。确实需要配置时，在对话中填写最少信息并确认；系统验证、应用配置，保留已完成工作后接续任务。设置页与对话入口读写同一份配置。

1.2 必须保持的约束

  • 不重置现有默认值；新安装也不猜测用户的外部服务账号、地址或密钥。
  • Agent 只能检查状态、提出变更，不能批准自己的提案。
  • 预览不触发外部请求；用户确认绑定具体提案版本、地址、验证动作和作用范围。
  • 配置写入成功、配置对任务生效、任务接续成功是三个不同结果。
  • 保存新配置不改写历史或已排队运行的快照。
  • 配置连接器不代替工具执行权限；既有权限卡和策略继续有效。
  • 明文密钥不进入普通消息、模型输入、SSE、工具轨迹或日志。

2.1 实现前必须知道的差异

  1. catalog_state 是 SQLite 中的一份目录 JSON，凭据位于独立加密表；SessionRun 列表使用会话文件和 mutateArray。不能把配置提交与创建 run 视为一个 SQLite 事务。
  2. createProvider 会写凭据并保存目录，materializeProviderModel、replaceSessionSettings 又各自保存。顺序调用三个现有方法不能满足原子提交，需要抽取无独立提交的内部操作。
  3. 已有 commitPluginSettings 提供“比较版本、写目录、写 receipt”的事务模式，但只覆盖 plugin 候选项；不能宣称它已经支持本功能。
  4. 创建会话的 HTTP 路由在未显式指定模型时已经允许 allowUnconfiguredModel。首次引导可以使用已有空会话，不需要先配置好模型才能进入对话。
  5. 当前连接测试会在缺少 token 时直接失败，且请求构造未完整按 apiProtocol/apiVariant 分派。新验证必须支持真实运行已经支持的协议及 tokenOptional，不得假造 token 绕过检查。
  6. SessionRun.settingsSnapshot 不保证提供方端点与密钥的所有依赖已经不可变。接续还须记录资源版本和生效前置条件，不能只检查模型 profile ID。
  7. 配置相关模块中已有未完成或其他任务的本地修改时，实施应在隔离分支/工作树进行；本次仅新增文档。

4. 能力目录和适配器

每个能力声明 id、schema 版本、允许范围、字段定义、敏感字段、验证计划、生效方式和撤销能力。Registry 是显式注册的有限集合；模型不能提交新的适配器、任意 JSON Patch、代码或文件写入路径。

建议内部接口（签名示意，辅助类型在实现时补全）：

TS
interface ConfigurationAdapter<Input, Plan> {
  readonly id: ConfigurationCapabilityId;
  readonly version: number;
  inspect(context: ReadonlyConfigurationContext): Promise<SafeCapabilityState>;
  normalize(input: unknown): Input;
  preview(input: Input, snapshot: ConfigurationSnapshot): Plan;
  verify(plan: Plan, context: ApprovedVerificationContext): Promise<VerificationResult>;
  apply(plan: Plan, transaction: ConfigurationTransaction): ApplyReceipt;
  previewReversal(receipt: ApplyReceipt, snapshot: ConfigurationSnapshot): Plan;
}
  • inspect 仅返回已有资源 ID、能力状态和缺项，不主动探测网络、不读取明文凭据。
  • preview 必须为确定性操作，无网络、无激活；验证计划中列出目标主机、请求种类、次数上限、是否可能计费。
  • verify 只能拿到已确认计划对应的凭据访问器，不能遍历凭据库。
  • apply 是同步事务内操作，不执行网络、文件安装或重启，不自行 COMMIT。
  • connector.enable 在读取最新有效集合后添加目标 ID，生成完整目标集合并保留其他项；既有连接器列表是整表替换，不能只传新增 ID 导致其他项被删除。
  • 项目/全局变更若被当前会话覆盖，预览必须明确列出附加会话变更或说明不会解决当前任务，禁止隐藏覆盖。

诊断代码至少包括 MODEL_MISSING、CREDENTIAL_REQUIRED、MODEL_CAPABILITY_MISMATCH、CONNECTOR_NOT_ENABLED。网络超时、限流和额度不足不能自动归为凭据错误。启用连接器前同时检查安装、配置与依赖可用性；缺失依赖不能静默连带启用。

5.2 内部实体

除 DTO 字段外，后端保存以下内容；显式投影为 DTO，禁止对象展开后再靠黑名单删字段：

  • schemaVersion、适配器版本、触发诊断依据、去重 fingerprint。
  • 源 submission ID 或 run ID、原任务引用、artifact/reference IDs。
  • 规范化输入、基线 overrides（含字段缺失）、资源版本向量、计划和 preview digest。
  • 绑定请求/字段/目标的凭据草稿引用，不是明文。
  • 确认记录、验证 attempt/结果、应用 receipt、反向变更计划。
  • continuation ID、候选 run ID、安全边界引用、取消 generation。

revision 在输入、scope、目标、验证动作或基线改变时递增，并使旧确认失效；stateVersion 在任何状态变化时递增。单纯验证进度不改变 revision。

5.3 状态流转

起点 事件 终点 关键条件
无 创建提案 collecting_input / awaiting_confirmation 有真实诊断或用户请求；按 fingerprint 去重
可编辑状态 preview collecting_input / awaiting_confirmation 规范化成功；未联网
awaiting_confirmation 用户确认 validating revision/digest、范围、权限和凭据有效
validating 验证通过、安全边界就绪 applying 版本仍匹配，未取消
validating 输入/连接错误 needs_fix 旧配置不变；反馈字段级错误
validating / applying 基线改变 stale 不执行覆盖，重新预览
applying 原子提交 applied 配置、receipt、接续意图一起持久化
未提交状态 拒绝 / Stop / 过期 dismissed / cancelled / expired 清理未引用草稿；不应用
applying 确定未提交的存储错误 failed 回滚数据库与内存目录

结果不明时先查 receipt，不能直接改成 failed 或重试。已 applied 的提案保持 applied；撤销创建新的反向提案，原记录通过 reversalRequestId 关联，保留历史。

配置 applied 之后接续失败只改 continuation 状态，不把配置伪装成未保存。相同请求每个 revision 最多有一次正式应用。

6. 持久化、事务与版本

6.1 新增表（逻辑设计）

全部使用现有 catalog.sqlite 和同一数据库连接，不另建包含正式配置值的配置库。建表迁移应幂等，版本记录使用本功能独立的 schema metadata，避免占用未经核对的全库 user_version。

表 核心字段与约束
configuration_requests id PK、session/project/run、source_submission_id、revision、state_version、state、expires_at、private_json；活动请求按 fingerprint 去重
configuration_request_revisions (request_id, revision) PK，不可变规范化计划、脱敏预览、基线和 digest
configuration_secret_drafts id PK、request_id、field_id、binding、ciphertext、expires_at、credential_version；不存明文
configuration_operations id PK、request_id/revision、operation_kind、idempotency_key、payload_digest、status、验证结果或应用 receipt；幂等键唯一
configuration_resource_versions resource_key PK、单调递增 revision；旧资源首次读取视为 0
configuration_outbox id PK、request_id/revision、kind、state、payload、候选 run ID；(request_id, revision, kind) 唯一
configuration_session_controls session_id PK、stop_generation；为重启后的停止语义提供持久依据

请求内部可保存阻塞的原始任务草稿，但不得把它当成“用户已经再次发送的消息”。(session_id, source_submission_id) 对有 submission ID 的请求加唯一索引；草稿内容沿用消息级存储权限、大小限制与引用验证。

草稿凭据空闲有效期默认 30 分钟，提案最长等待 24 小时；有效期不因 SSE 重连自动延长。凭据过期后卡片要求重新输入并重新预览。已确认的验证/应用操作持有有界的执行租约，清理器不得删除其正在使用的凭据；操作完成后转正式密钥或清理草稿。

6.2 统一条件写入

不能只为新卡片增加 revision。旧设置页、provider/model 更新与删除、plugin 配置以及会话覆盖写入，也必须更新相关版本。否则用户在另一窗口修改配置后，旧卡片仍会误判基线有效。

资源版本向量包含：目标 overrides、会影响继承结果的父级、选定 provider/model、凭据 generation，以及连接器安装/配置状态。非数据库管理的 registry/策略使用确定性指纹并在提交前再检查；指纹不包含密钥明文或明文 hash。

写入使用白名单操作，在最新 overrides 上变更目标字段；不把 Agent 看见的旧完整对象 PUT 回去。保留未涉及字段、插件配置和 inherit 语义。版本冲突返回新预览，不自动合并后继续使用旧确认。

6.3 原子提交算法

TEXT
1. 网络验证在事务外执行，持久化验证 attempt 与结果。
2. 等待对应运行安全边界；检查会话/项目未归档、未删除。
3. 进入共用的 settings/model 写入串行边界，等待已有 saveQueue。
4. 在事务外准备新的不可变候选目录；BEGIN IMMEDIATE 后不再 await。
5. 重新比较 revision、资源版本、stop_generation、验证计划和有效期。
6. 同一事务写入：正式 provider/model/密钥、overrides、资源版本、
   applied 状态、应用 receipt、事件 outbox 和 continuation outbox。
7. COMMIT 后更新内存目录，并触发已有配置变化通知。
8. 事务外发布脱敏事件及处理接续；失败可从 receipt/outbox 恢复。

候选目录必须基于进入串行边界后的最新状态构造；若构造需要异步步骤，回到事务前重新读取并比较。事务中只执行同步 DB 操作。现有 mutator 要拆出不独立持久化的内部操作，不能在本事务内调用会排队/提交的公共 mutator。

实现必须核对所有正式目录/凭据写入入口是否遵守相同的写入边界。事务失败恢复内存原对象，且 saveQueue/锁队列不能因一次失败永久卡死。首版沿用单 API 进程写入模型，不宣称支持多个进程同时修改同一数据目录。

6.4 撤销

从原 receipt 生成反向提案，展示差异并经过同一确认/条件提交链路。保留原来字段“不存在”的信息，才能恢复继承；不要把旧 effective 值写成新 override。

默认撤销选择/绑定，保留新建共享资源。只有资源未被引用且另有明确删除确认时才删除；首版卡片不顺带删除 provider。外部测试请求和已经完成的业务动作不能撤销。由于首版凭据修复默认建立新连接，撤销无需在历史记录中保留旧密钥明文。

7. HTTP 与 Agent 工具契约

以下均为拟新增接口。所有用户接口沿用现有 bearer 鉴权，验证 route 中的 session/project 归属和可写状态；全局配置遵循当前部署的配置管理权限。当前认证模型不提供独立用户身份时，审计记录“已认证客户端”，不得伪造 userId 或声称具备多租户隔离。

7.1 路由

前缀 S = /api/sessions/:sessionId，R = S/configuration-requests/:requestId。

方法与路径 语义 响应
POST S/configuration/preflight 确定性检查任务所需基础配置；不足时保存阻塞任务草稿并生成卡片 200 ready 或 200 configuration_required，不启动 Agent
GET S/configuration-requests 分页获取脱敏快照，默认待处理项及近期结果 200 {items, nextCursor?}
GET R 获取单张卡片，恢复验证/应用进度 200 ConfigurationRequestView
POST R/credentials 提交指定 credential 字段到加密草稿 201 {handle, expiresAt}，只返回给浏览器
POST R/preview 合并用户字段与凭据 handle，生成确定性新版本 200 卡片 DTO；不联网
POST R/decisions 确认应用、仅探测模型列表或拒绝 首次接受异步操作 202；重复提交返回原操作
POST R/continue 已 applied 后单独重试/启动接续，不再次写配置 202，或已存在接续的 200

所有写请求携带 Idempotency-Key。同键同规范化载荷返回同一结果，同键不同载荷返回 409 IDEMPOTENCY_MISMATCH。不同键也不能绕过同一 revision 的应用唯一约束。

preflight 只检查确定性前置条件，不为了猜测用户意图额外调用模型或探测网络。正常 /runs 创建也执行同样的基础检查，防止预检后配置变化；不足时返回结构化 409 CONFIGURATION_REQUIRED 和可重用 request ID，而不是普通字符串错误。复用客户端 submission ID，避免预检与正式提交产生两张卡。

7.3 统一错误

HTTP code 前端行为
400 INVALID_CONFIGURATION_INPUT 定位具体字段，不丢弃其他输入
401 / 403 UNAUTHENTICATED / CONFIGURATION_FORBIDDEN 沿用应用鉴权处理，不变成“API Key 错误”
404 CONFIGURATION_REQUEST_NOT_FOUND 移除无效入口，不切换到别的会话
409 STALE_CONFIGURATION_PREVIEW / RESOURCE_VERSION_CONFLICT 展示最新差异并重新确认
409 SESSION_NOT_WRITABLE / CONTINUATION_STOPPED 显示停止/归档原因，禁止自动恢复
409 IDEMPOTENCY_MISMATCH 保留原操作，拒绝用同键改参数
410 CONFIGURATION_EXPIRED / CREDENTIAL_DRAFT_EXPIRED 重新输入或重建提案
429 CONFIGURATION_RATE_LIMITED 显示重试时间，不自动密集验证

验证失败通常是异步操作结果：卡片进入 needs_fix，附 AUTHORIZATION_FAILED、MODEL_NOT_FOUND、NETWORK_UNREACHABLE、RATE_OR_QUOTA_LIMITED、UNSUPPORTED_PROTOCOL、CAPABILITY_UNVERIFIED 等领域代码。未知 provider 错误只返回脱敏摘要。

7.4 Agent 工具

inspect_configuration 输入限制为当前任务相关能力和资源 ID，返回脱敏有效值、来源、缺项和支持的操作。propose_configuration 接收 capability ID、已知非敏感字段、原因/诊断引用和建议范围，返回 request ID 与卡片状态。工具参数拒绝明文 apiToken、headers、任意 env、URL 内嵌 userinfo 和通用文件路径。

两工具通过现有 extraTools 与工具策略入口注入主 Agent；子 Agent 不注册，不能仅依靠提示词禁止。inspect 可声明并发安全；propose 是排他工具，并按 session/run/能力/目标/缺口生成 fingerprint。拒绝后的同缺口在该任务内抑制重提，用户主动请求或实质输入变化可开启新提案。

工具调用不得获得 bearer、credential handle、决定接口或批准能力。工具执行先持久化提案并返回；等待用户发生在完整工具步骤的安全边界，避免工具自己阻塞、同时等待兄弟工具完成所形成的死锁。

8. 验证与凭据通道

8.1 验证必须在保存前完成

把当前连接测试拆为“根据显式协议生成请求”和“执行有界请求”两个部分，接受未保存的 provider/model 草稿，不要求先创建正式 provider 才能测试。设置页的测试入口也使用同一个验证实现，避免两条路径结果不一致。

项目 首版契约
协议 按规范化后的 apiProtocol / apiVariant 使用真实运行对应的请求格式与路径；禁止只凭 hostname 猜协议
无密钥端点 Registry/现有 provider 明确允许 tokenOptional 时可省略凭据与 Authorization；缺钥的收费端点仍提示补齐
内容 使用固定、无用户数据的探测输入；不得发送用户任务、图片、文件或聊天历史

“连接成功”不代表“视觉能力已验证”。分开记录 connectivity 和 required capability 的依据：提供方事实、已有 profile 声明或专门探测。需要专门探测时把固定测试内容、次数和潜在费用放入同一验证计划；能力未知时显示未验证，不能仅因为一个文本请求成功就自动设置 vision=true。

已有 ModelConnectivityTestCoordinator 只在进程内按 model ID 合并，不能替代持久幂等。新 attempt 按 request/revision/验证计划建立唯一操作记录；同一未变更 revision 的重复点击读取原操作。验证失败后的显式重试生成新的 attempt，并记录用户授权，不能覆盖旧结果。

8.2 未知模型 ID 的两步流程

  1. 卡片收集地址、协议和凭据；preview 展示“获取此服务的模型列表”及目标。
  2. 用户批准 discover_models，验证器只执行该计划，结果保存为有限且脱敏的候选集合。
  3. 用户选择模型；产生新的 preview revision，展示实际将新建/绑定的资源与测试计划。
  4. 用户批准 apply 后再验证并提交。

如果服务不支持模型列表，返回可操作的提示并允许手填模型 ID。未知协议不能自动切成另一协议、转送凭据或替用户选择外部服务。已知模型 ID 且预览完整时仍可一次确认完成。

9. 运行等待与任务接续

9.1 活跃运行的安全边界

当前 Runtime Core 支持完整步骤后的 TurnLifecycle.afterTurn，但返回类型是 Promise<void>，尚无正常“交回控制权”结果。不能在文档中假设已支持无损暂停。

本版采用最小通用扩展：afterTurn 可返回 void | { kind: "yield" }，默认 void 保持原行为；loop 的结果增加可选 stopReason: "yielded"，正常完成保留兼容语义。Core 只增加中性的 yielded 终态和对应生命周期记录，不了解配置、审批、provider 或接续 run。实现时同步更新并版本化 Runtime Core 架构说明。

API 侧用组合 lifecycle 顺序调用现有版本记录器，再执行配置边界协调器；版本记录必须成功后才能 yield。模型无工具的结束步骤与含工具步骤都遵循同一规则，不遗漏任何调用点。yield 不能伪装成 exception、用户取消或 completed；必须穿过 native-agent/AgentRun 的返回值和事件映射到产品层。

具体流程：

  1. propose 工具持久化提案并返回 pending；UI 可显示卡片。
  2. 当前工具批次继续按照已有调度规则完成。确认可以先记账，网络验证可以提前进行，但正式配置提交与接续要等待安全边界。
  3. afterTurn 确认本批所有工具结果已持久化、assistant/tool-call 配对完整，并核查关联子任务或外部作业是否还有未决状态。
  4. 记录 checkpointRef，进入配置外部等待；运行显示 blocked 和结构化 blockedReason={kind:"configuration",requestId}。
  5. 用户拒绝且有替代路径时释放等待，给 Agent 注入脱敏拒绝结果，再按旧配置继续；没有必要能力时停止当前任务并保留原因，不循环重提。
  6. 配置成功、选择 apply-and-continue 后，协调器返回 yield；产品层把旧 run 记为 interrupted、terminationReason=configuration_changed。
  7. 旧运行的文件、事件和 usage 收尾完成后才标记 continuation outbox 可投递，避免新 run 在旧 run 清理前开始。

external wait 使用已有引用计数，并在 finally 中释放。等待用户时暂停相应 Agent 超时；独立执行中的工具仍遵循自己的执行超时。卡片在并行工具未结束时显示“等待当前步骤完成”，不能声称已切换模型。

如果后台作业存在未知结果，接续进入 needs_user_action。能查询状态的作业先查询；不得通过重发上传、付费请求或远程命令猜测是否完成。用户 Stop 始终优先于自动接续。

9.2 首次配置与已经失败的运行

首次进入使用现有无模型会话创建路径，前端保留 composer 草稿；preflight 将需要恢复的原任务及引用保存为阻塞 intent，不创建必然失败的 run。配置成功后用相同 intent 创建第一个 run，并只生成一条用户消息。离开页面再回来通过卡片与 intent 恢复，不依赖模型记住初始请求。

运行已经因模型认证失败而结束时，在错误归因层生成同类卡片，旧 run 维持 failed 历史。确认后创建有来源关联的后续 run，不把既有失败记录追溯改成“等待配置”。若其他工作仍在执行，仍须完成安全性核查。

9.3 接续载荷与来源

ContinuationIntent 至少保存：

TEXT
continuationId, requestId, requestRevision, sessionId
sourceRunId? / sourceSubmissionId
candidateRunId, checkpointRef?, sourceUserMessageId?

新 SessionRun 增加 optional 字段：continuedFromRunId、configurationRequestId、continuationId、terminationReason、blockedReason。这些字段由服务端设置；普通 /runs body 不能伪造内部接续身份。历史记录缺少字段时使用原行为。

接续上下文是新的运行装配：原任务目标、已完成步骤的事实记录、产物引用、最后安全点和未完成事项。使用已有 ContextAssembler/历史窗口机制；跨模型时重新适配上下文，不直接复制不兼容的 provider 专属隐藏字段。不能把配置表单或凭据写成假冒用户聊天消息。

恢复前检查附件/产物仍存在且可访问、原有 skill revision 可解析、当前会话未归档、候选资源版本仍有效。缺项时要求用户处理，不静默换模型、换资源或补造证据。

9.4 跨 SQLite 与文件的幂等接续

不尝试用 SQLite 事务包住 run 文件写入。使用持久 outbox、预先分配的候选 run ID 和文件写屏障：

TEXT
配置提交事务：写 applied receipt + continuation intent + candidateRunId
    ↓
旧 run 收尾完成：outbox 从 waiting_boundary 变为 pending
    ↓
确认来源、停止 generation、资源前置条件仍有效
    ↓
在 sessionRunsPath 的同一个 mutateArray 屏障内：
  按 continuationId 查找 → 已存在则返回该 run
  不存在则用 candidateRunId 和冻结快照插入 queued run
    ↓
将 runId 回写 outbox，并发布 queued 事件、唤醒现有调度器

新增内部 ensureContinuationRun，不能在外部“先 list、再普通 createSessionRun”，那会留下并发重复创建窗口。插入前再次验证会话控制 generation；已有 run 无论 queued、running 还是终态均返回同一个结果，不重建第二个 run。

默认沿用队列追加语义，保留已有 queued run 的相对顺序与快照。如果前面已有任务，卡片显示“已配置，接续任务已排队”，不能直接显示“正在继续”。本版不引入队列插队策略。

调度器在接续 run 从 queued 进入 running 前，再核查 outbox 未抑制、来源 run 已终态、generation 和资源版本仍匹配。即便 run 文件已写入而 DB 回执尚未回写，也必须能以 continuationId 查询权威记录；不能只依赖 UI 状态启动。

完整 approvedSettingsSnapshot 在提交前通过既有装配逻辑准备，提交时检查其依赖版本；涉及异步固定 skill 等引用时在事务外完成，事务内只比较。重启后使用已批准的快照，不重新解析当前值悄悄改变用户批准的内容。排队期间依赖变化，标记 needs_user_action 并暂停该接续，不改变普通 queued run 的既有行为。

10. SSE、快照与前端实现

10.1 事件模型

扩展 RunStreamEvent：

TS
type ConfigurationEvent = {
  type: "configuration.required" | "configuration.updated" | "configuration.resolved";
  request: ConfigurationRequestView;
};

实体的 session/run ID 与事件外层身份必须一致。事件携带全量脱敏卡片快照，减少增量补丁丢失导致的错误；使用 request.stateVersion 合并，只接受更新版本。同内容 revision 下仍可能有新验证/接续状态，因此不能只比较 revision。

事件产生与 DB 状态变化通过 outbox 关联，发布是至少一次投递。页面切换或重新订阅时同时读取配置实体快照；run 终态流已关闭后，由操作响应和对 pending 操作的有界轮询补齐状态。轮询在终态/页面不可见时停止或退避，不能假设终态 run 还能持续收到 SSE。

首次配置没有 run ID，归于当前 session 的对话尾部；创建第一个 run 后通过 request/intent 关联移到对应任务，只展示一次。浏览器地址中的 request ID 不能作为越过 session 归属校验的依据。

ConfigurationCard 接收 DTO 和 callback，不直接访问其他设置组件内部状态。建议拆分字段渲染、差异预览、验证状态和结果区；敏感字段仅在组件的瞬时内存中存在。

11. 数据迁移、上线和回退

  1. 先新增表与可选 schema 字段，历史 run、事件和目录无需整体重写；首次启动迁移重复执行不丢数据。
  2. 资源 revision 的初始化只补缺项，不改已有设置值；旧资源视为 revision 0 后第一次正式变更递增。
  3. 发布功能开关建议为 SCIENCE_AGENT_CONVERSATIONAL_SETTINGS_ENABLED（拟新增部署开关，默认关闭用于联调）；关闭时不注册 Agent 提案工具、不主动生成配置卡。完成验收后再决定发布默认值。
  4. 开关关闭仍能读取已存在记录、取消等待和清理凭据草稿；拒绝新的应用/接续。它不回滚已经应用的配置。
  5. Session 删除清理其提案、凭据草稿、outbox 和控制记录；全局 provider/model 按现有资源删除规则处理，不因一个会话删除就自动删除共享连接。清理范围扩展到现有删除影响预览。
  6. 上线采用同版本前后端。新可选字段读取兼容不代表任意旧二进制降级都安全：降级前排空/抑制配置接续、清理未用凭据、备份数据目录并做兼容验证；不能仅靠旧代码忽略字段而允许继续调度。

日志记录 requestId/revision、capability、诊断码、作用域、变更字段名、耗时、提交/接续结果。禁止记录密钥、handle、认证 URL、请求体和 provider 原始响应。运维统计区分验证失败、应用失败、接续失败与用户拒绝，不把正常交接计入模型故障。

CFG-T14 adapter + 并发 API 恢复继承；不覆盖后续变更、不删除被其他会话使用的资源
CFG-T15 前端 + 旅程 键盘操作、错误提示、窄屏和中英文均可用

13.2 必须补充的工程断言

  • 每个 HTTP 写路由的同键重放、异键同 revision、同键不同载荷。
  • 在 §9.5 每个窗口注入进程退出；保存后重启返回同一 provider/model/run ID。
  • 通用 yield 的无工具步骤、有工具步骤、usage、生命周期终态、版本记录顺序；不再发下一轮模型请求。
  • propose 与普通工具同批时，全部工具结果提交后才交接；子任务未决时不自动重放。
  • 新 run 在 file 写入与 DB 回写间崩溃，以及 queued 后被 Stop，再重启均不开始执行。
  • 手动设置页调用与对话提交交错；一次 DB 错误后下一次配置仍能保存。
  • 继承连接器集合添加一项保留其余项，撤销后重新继承；项目父级变化使预览失效。
  • 所有正式支持的模型协议各一个成功/不匹配用例；连接成功与视觉能力未知必须不同状态。
  • 重定向、URL 内嵌凭据、handle 越域、原始 provider 响应携带测试密钥时不会泄漏或转送。
